## Shared autonomous development

For an authorized nontrivial development Goal, use the `autonomous-development` skill automatically. Read the highest Goal, all requirements/acceptance criteria, current implementation, authoritative state and next action before editing. Keep project-specific instructions, stopped work, Human Gates, existing permissions and cost limits. Never replace another project's Goal or unscoped Compass state.

An owner development Goal delegates routine research, design, planning, decomposition, reversible implementation, tests, repair and integration choices. Proceed without repeated plan/design/worktree/process confirmation when scope is clear. This standing owner preference takes precedence over workflow-skill process-approval suggestions; missing material requirements, new authority and irreversible or safety-sensitive boundaries still require the appropriate user input.

Decompose the remaining work and dependencies. Run independent useful work concurrently through native subagents; do not serialize it without a concrete reason. Choose actual concurrency from the task graph, current memory/CPU/load, available usage, native limit and tighter project limits using the installed preflight. Logical roles are not simultaneous slots. Small or tightly coupled work may run alone. Assign architecture, backend/frontend/data/AI, tests/security/performance/diagnosis and independent verification as needed. Inherit the user's model; no paid fallback.

Give every worker an objective, owned files or worktree/branch, forbidden files, dependencies, acceptance criteria and checks. Preserve unrelated edits. Keep a single integrator for shared files. Test and review independent parts concurrently; integrate verified parts as they finish, diagnose failures and continue unaffected work. Reuse the project's resource-admission lane for heavy commands.

Measure progress by working verified features. On failure, preserve evidence, investigate cause and change hypothesis/strategy before repeating. Keep bounded attempts and resource budgets; do not abandon an achievable Goal merely because one approach failed. Continue safe actionable work until acceptance is met or a real stop condition applies. Respect user stop/pause/cancel, approval waits, missing authority, limits and safety boundaries immediately.

Persist Goal, requirements, criteria, task/dependency state, evidence, failure cause and next action in the existing GitHub/project mechanism. Chat alone is insufficient. Read it on resume; do not reset attempts or consumed budgets. Hooks are opt-in checks over that state, never a new Goal authority. For a new project without a state mechanism, use the skill's small repository-owned state file.

Completion requires functional artifacts plus relevant tests, independent review and actual runtime/data evidence. Code, CI, GitHub, plans and scheduled execution alone are insufficient. Report unsupported capabilities and unmet conditions plainly. Do not mark synthetic tests as real hardware/session evidence. Configuration or hook updates require backups, exact-diff review, affected checks and a reversible restore path. Use normal hook trust review; never write trust records or bypass approval.
