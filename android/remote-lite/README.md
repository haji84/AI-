# GORIQ Remote Lite Android candidate

This is an independent `app.goriq.remote.lite` Android project with a P-256 AndroidKeyStore identity, Japanese invitation/owner-approval setup, bounded system-validated HTTPS, and a local Accessibility screenshot/gesture service. It includes no GORIQ Worker, AI, task executor, device administrator, boot receiver, public listener, or GORIQ owner credential.

The APK is **not ready for a friend**. Release can submit device enrollment to an operator-supplied HTTPS coordinator but still has no public owner-account service, native WebRTC media/DataChannel transport, off-device viewer, Android 9/10 capture path, or unattended reconnect. A `goriqremote://enroll?server=<encoded HTTPS origin>&invite=<48 hex>` invitation is only a preview until a local registration tap. Pending metadata survives process restart; invitations are not saved and an uncertain request is never automatically resubmitted. A changed server cannot replace an existing enrollment silently.

The screenshot diagnostic works only on Android 11+ after a person enables Accessibility. Secure/locked screens are refused. The OS owns the permission dialog. Fresh image dimensions/byte count are diagnostic output, not live remote video.

The shared coordinator exchange also validates and signs SDP/ICE with a SHA-256 binding to the exact Node canonical JSON. Signed polling acknowledges only after the caller applies a signal; the last session/cursor is committed before memory advances and survives process restart. The VM uses synthetic SDP/ICE to check actual AndroidKeyStore/Node interoperability. This is a signaling prerequisite, not a native WebRTC connection. Cursor storage does not restore the peer or media consent; the native transport must renegotiate after restart and close on failed cursor persistence.

The `debug` variant adds a VM-only diagnostic activity and a generated two-day loopback test certificate trust anchor. Both variants reject cleartext HTTP. The Android 15 VM harness uses normal setup over HTTPS through ADB reverse, fixture owner fingerprint approval, signed discovery/acceptance/status, process-stop recovery, and status-gated real capture/tap followed by revocation. The fixture owner is synthetic; this is not physical human acceptance or production login. Status-before-operation does not make revocation atomic. **Never distribute the debug APK.** Release manifest/archive inspection requires INTERNET while rejecting debug certificate trust, the VM certificate and debug activity. CI does not publish, sign or deploy an APK.

Before a debug build, run `python scripts/prepare_vm_tls.py` from this project with JDK 17 `JAVA_HOME` set (or pass `--keytool`). It generates the test key/certificate only under ignored `app/build/`; release does not consume them. Then run `gradle :app:testDebugUnitTest :app:assembleDebug :app:assembleRelease`. All server resources in the VM fixture bind only `127.0.0.1`.

The VM UI harness also builds `:vm-ui-probe:assembleDebug` and installs that separate test-only APK with `adb install -t`. Its self-instrumentation reads the visible hierarchy with Android's `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`: the ordinary `uiautomator dump` command can suppress the very service being tested. The probe has no network permission, does not target/restart the product process and is never part of the product APK. Failed enrollment can be retried with a new same-origin invitation only after an explicit local confirmation that the owner checked the expired old request; the key and prior receipts are retained.

Rollback: revert this feature's commits. Builds create only disposable local debug TLS fixtures. Actual user-triggered enrollment metadata and AndroidKeyStore identity must be retained during rollback; no app-data deletion or silent re-pairing is part of it.
