Issue #1831 owner approval (2026-10-22, this task): add the normal `ACCESS_NETWORK_STATE` permission for WebRTC network observation. It does not grant screen/input access; those retain their separate visible OS consent. The SDK now uses its Android network monitor when granted, with the existing permission-free interface-enumeration fallback retained. Public hosting is still unavailable: the owner reports the separate Oracle account is not prepared.

This is an independent `app.goriq.remote.lite` Android project with a P-256 AndroidKeyStore identity, Japanese invitation/owner-approval setup, bounded system-validated HTTPS, and a local Accessibility screenshot/gesture service. It includes no GORIQ Worker, AI, task executor, device administrator, boot receiver, public listener, or GORIQ owner credential.

The APK is **not ready for a friend**. Release can submit device enrollment to an operator-supplied HTTPS coordinator. Native WebRTC MediaProjection video and ordered manual input are now implementation candidates undergoing VM acceptance. Public owner accounts, public ICE/HTTPS configuration, Android9–13 safe remote input, distribution signing and unattended reconnect remain unavailable. A `goriqremote://enroll?server=<encoded HTTPS origin>&invite=<48 hex>` invitation is only a preview until a local registration tap. Pending metadata survives process restart; invitations are not saved and an uncertain request is never automatically resubmitted. A changed server cannot replace an existing enrollment silently.

The screenshot diagnostic works only on Android11+ after a person enables Accessibility; its success alone does not prove safe remote input into a target window. Native remote input additionally requires Android14+ window-specific screenshot success, unchanged window ID/bounds/display, unlocked interactive screen, a fresh signed session status and an unexpired local lease. Window metadata is used for ID/bounds/layer checks; element content is not collected. The OS owns permission dialogs. No system permission or secure-window bypass is included.

Screen sharing requires an explicit local session selection and fresh OS consent, followed by a visible foreground service with a Stop action. Status uncertainty, lock/screen-off, local stop, peer loss or OS sharing termination closes publication/input. The UI does not report stopped until native cleanup completes; failed cleanup is explicit. A signed coordinator session-end follows local shutdown and reports uncertainty independently. Already-issued gestures may finish after stop; new dispatch is serialized with stop. Android14+ consent cannot be silently reused after reboot.

The shared coordinator exchange validates and signs SDP/ICE with a SHA-256 binding to the exact Node canonical JSON. Signed polling acknowledges only after the caller applies a signal; the last session/cursor is committed before memory advances and survives process restart. The actual AndroidKeyStore/Node synthetic signaling check passed at7a41a9d3. Cursor storage does not restore a peer or media consent; start a new session after media/process termination. Native media evidence must be read separately from exact-head CI.

The `debug` variant adds VM diagnostic/secure-window activities, a generated two-day loopback TLS trust anchor and a relay-only loopback TURN service configuration. Both variants reject cleartext HTTP. The Android15 VM harness extends normal HTTPS setup, real AndroidKeyStore enrollment and restart checks with separate Chromium native screen video, actual target taps/ACK/pixel change, secure-window refusal, and Android-driven revoke shutdown. Device HTTPS requests add100ms each. TURN binds only127.0.0.1; the Android VM uses its host-loopback alias10.0.2.2 and the browser uses127.0.0.1. HTTPS separately uses ADB reverse. The public fixture password and loopback-peer exception never enter release. These tests do not prove Internet/NAT/iPhone/40-device acceptance. **Never distribute the debug APK.** Release inspection rejects VM components/trust/resources and requires all native SDK notices. CI does not publish or sign a distribution APK.

Before a debug build, run `python scripts/prepare_vm_tls.py` from this project with JDK 17 `JAVA_HOME` set (or pass `--keytool`). It generates the test key/certificate only under ignored `app/build/`; release does not consume them. Then run `gradle :app:testDebugUnitTest :app:assembleDebug :app:assembleRelease`. All server resources in the VM fixture bind only `127.0.0.1`.

The VM UI harness also builds `:vm-ui-probe:assembleDebug` and installs that separate test-only APK with `adb install -t`. Its self-instrumentation reads the visible hierarchy with Android's `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`: the ordinary `uiautomator dump` command can suppress the very service being tested. The probe has no network permission, does not target/restart the product process and is never part of the product APK. Failed enrollment can be retried with a new same-origin invitation only after an explicit local confirmation that the owner checked the expired old request; the key and prior receipts are retained.

Rollback: revert this feature's commits. Builds create only disposable local debug TLS fixtures. Actual user-triggered enrollment metadata and AndroidKeyStore identity must be retained during rollback; no app-data deletion or silent re-pairing is part of it.
