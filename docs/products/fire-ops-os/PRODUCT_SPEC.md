# AI消防業務OS 現行完全仕様書

2026年10月2日時点

## 1. システムの目的

消防本部の業務全体を対象に、AIと共通データ基盤を使って、

- 二重入力を減らす
- 報告書・帳票作成を自動化する
- 入力・計算・記載ミスを事前に検出する
- 月報、年報、統計、手当、予算等を自動集計する
- 各本部独自の条例・規則・運用に対応する
- 人事異動や制度変更にも追従する
- 長期間、安全に運用できる

ことを目的とする。

単なる「報告書AI」ではなく、**消防業務全体を扱うモジュール型AI業務OS**とする。

# 3. 最重要データ原則

固定原則は、

**「事実は一元管理し、訂正は履歴付きで更新する。帳票・集計・関連業務は、その事実を再利用して生成する」**

とする。

「1回入力したら絶対変更しない」という意味ではない。

訂正時には、

```
現在値
変更前の値
変更後の値
変更日時
変更者
訂正理由
根拠
承認情報
```

を保持する。

旧値を削除して上書きするだけにはしない。

---

# 4. データ再利用

一度登録された情報は、権限・目的・ルール上問題がない限り全モジュールで再利用する。

例えば1回の出動情報から、

```
出動報告書
個人出動実績
勤務実績
時間外
手当
車両運行実績
運行日誌
月報
年報
統計
```

へ連携する。

同じ時刻・職員・車両等を業務ごとに再入力させない。

---

# 5. 訂正時の伝播方式

採用方式はB方式。

### 未確定資料

自動更新。

### 確定済み資料

勝手に書き換えない。

訂正前に影響範囲を表示する。

```
出場時刻
10:32 → 10:35

影響
救急報告書
個人出動実績
時間外
手当
月報
運行日誌
統計
```

さらに、

```
どの資料が変わるか
どの項目が変わるか
変更前
変更後
自動更新されるか
再承認が必要か
```

まで表示する。

これを**影響範囲プレビュー**とする。

# 10. AI安全設計

AIが不明な内容を勝手に確定しない。

状態として、

```
確定
要確認
根拠不足
読取不能
不明
```

を持つ。

例えば、

```
現場到着時刻
14:32

確信度：低
要確認
```

と表示。

PDFや画像から読み取った場合は、**元資料のどこを読んだか**を確認できるようにする。

共通コアは、各業務モジュールより先に構築する。

```
↓

↓

```

## 95.1 職員とログインアカウントの分離

職員情報とログインアカウントは別管理とする。

職員は `employee_id` 等の不変IDで識別し、ログインIDの変更、人事異動、役職変更があっても職員履歴が壊れない構造にする。

基本的な論理エンティティは、

```
users
employees
organizations
assignments
roles
permissions
role_bindings
delegations
login_history
audit_logs
modules
```

とする。

具体的なDB製品・物理テーブル定義・カラム定義は未確定とする。

## 95.2 ログイン認証

基本ログイン方式は、

```
職員ID
＋
パスワード
```

とする。

パスワードは平文保存しない。安全なハッシュ方式で保存する。

ログイン成功後は職員を一意に特定し、その職員の現在の所属・役職・担当業務・有効な役割を取得する。

MFA、SSO、外部ID基盤連携、セッション方式等の認証詳細は現段階では未確定とする。

## 95.3 権限の自動算出

権限は、

```
職員
＋
現在の所属
＋
現在の役職
＋
担当業務
＋
正式な権限ルール
```

からルールエンジンが算出する。

AIが独断で権限を付与・拡張・剥奪してはならない。

AIは、

```
権限変更候補
承認者変更候補
担当変更候補
影響範囲
```

を提案できるが、正式な適用は承認済みルールと管理者確認に従う。

## 95.4 RBAC

権限モデルは役割ベース（RBAC）を基本とする。

同一職員でも業務モジュールごとに異なる役割を持てる。

例：

```
救急
閲覧：可
編集：可
承認：可

勤務
閲覧：可
編集：一部可
承認：不可

予防
閲覧のみ

財務
権限なし
```

権限は少なくとも、

```
閲覧
作成
編集
削除
承認
出力
印刷
外部共有
管理
```

等の操作単位で制御できる構造とする。

## 95.5 人事異動と権限連携

人事異動時は、

```
所属変更
↓
権限変更候補
↓
承認者変更候補
↓
担当変更候補
↓
影響範囲表示
↓
管理者確認
↓
施行日反映
```

とする。

旧所属の権限は施行日時点で失効し、新所属・新担当に基づく権限を同日時点から有効化する。

過去案件を表示する場合は、現在の役職ではなく当時の所属・役職・権限履歴を参照可能にする。

## 95.6 代理承認・期限付き権限

代理承認・期間限定権限に対応する。

保持する情報の例：

```
代理元
代理先
対象業務
付与権限
開始日時
終了日時
理由
承認情報
```

期限終了後は自動失効する。

恒久権限へ勝手に昇格させない。

## 95.7 監査ログ

共通コアで最低限、

```
ログイン
ログアウト
閲覧
新規作成
変更
削除
承認
否認
権限変更
代理権限付与・失効
出力
印刷
外部共有
```

を追跡可能にする。

監査ログは通常の業務データとは分離し、一般利用者が任意に改変できない構造にする。

## 95.8 ログイン後ホーム

ログイン後は、本人の権限・所属・担当業務に応じて表示内容を変える。

共通ホームには、

```
今日やること
承認待ち
期限が近い案件
期限超過
自分の担当案件
通知
```

等を表示する。

権限のない業務・情報は原則として表示しない。

## 95.9 人事異動資料のAI読取

人事異動資料をAIで読み取り、

```
氏名
旧所属
新所属
役職
配置先
異動日
```

等を抽出する。

その情報から職員・所属・担当・権限変更候補を生成する。

AIの抽出結果だけで本番権限を直接変更してはならない。管理者確認後、施行日に反映する。

## 95.10 最初の実モジュール

共通コアに最初に組み込む実モジュールは、既に試作・検証を進めている **救急搬送分析** とする。

救急搬送分析は、

```
CSV / Excel取込
対象データ自動判定
月別・年別集計
搬送先別件数・割合
事故種別 × 搬送先
重点4分類
詳細ドリルダウン
検算
PDF / 紙資料出力
```

等を扱う。

このモジュールを共通コアへ統合することで、認証・権限・監査ログ・共通データ・帳票生成の最初の実運用検証に使用する。
