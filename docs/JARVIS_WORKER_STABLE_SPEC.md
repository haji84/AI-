# JARVIS Worker Stable Specification

Status: frozen baseline for Commander v5 + Android Worker 0.4.x.

## Architecture boundary

- Commander: chooses what to run, assigns devices, displays progress and errors.
- Broker: authenticates devices, queues tasks, stores state/results, transports commands.
- Android Worker: generic device execution engine. It must not embed business-specific success rules.
- Workflow Recipe: ordered, bounded steps that describe a concrete job such as the TikTok Lite spreadsheet flow.

A feature change in one layer must not silently redesign another layer's UI or contract.

## Commander v5

- Keep the proven v4.1 control layout.
- Device enrollment is one independent panel/button.
- The visible Commander must not expose temporary enrollment tokens, 10-minute URLs, QR codes, or expiry values.
- The fixed enrollment URL may be reused. Opening it mints a fresh one-device, 10-minute enrollment grant and redirects into the existing enrollment flow.
- Existing quick actions, range assignment, per-device assignment, bulk execution, per-device execution and result display remain compatible.

## Android Worker

### Lifecycle

- Runs as a resident foreground command service after enrollment.
- Restarts after BOOT_COMPLETED and package replacement.
- Reconnects by polling/heartbeat after temporary Broker/network failure.
- Locked devices are not bypassed. A secure locked device requires human unlock.

### Generic execution

The Worker executes bounded recipes. Supported generic primitives include:

- open app / settings / URL
- wake device
- click text / view id
- set text
- wait
- wait for package
- wait for one of several texts
- wait for a success/error outcome
- select a spreadsheet cell
- open the visible URL in the selected cell
- back / home / recents
- relative tap/swipe, with absolute coordinates retained only for compatibility

Each UI step may request 0..3 bounded retries. Infinite retry is prohibited. Failure stops the recipe and reports the failing step.

### Spreadsheet rule

Cell coordinates are the source of truth. Business labels are presentation only.

`open-sheet-cell-link` performs only generic mechanics:

1. verify Google Sheets is active,
2. navigate to the requested cell,
3. find a visible URL for that cell,
4. open it.

It does not know what “goldfish”, “QR”, TikTok Lite, or any business success screen means.

### Workflow recipe rule

Business-specific texts and completion rules belong in the recipe generated by Commander. The current TikTok Lite recipe explicitly verifies:

- the spreadsheet opened,
- the first configured cell URL opened,
- the first-stage success/error screen,
- return to Sheets,
- the second configured cell URL opened,
- the second-stage success/error screen,
- final return to Home.

A click alone is never success; the recipe must verify the expected post-click state.

### Device telemetry

Heartbeat should expose enough information for fleet operation:

- ready/working
- battery percentage
- charging state
- network connected/validated and transport
- screen interactive state
- lock state
- current foreground package when Accessibility can observe it
- Worker version/version code
- current task id/type
- current step index/action
- task start time
- last completion time
- last error
- device owner/admin/accessibility state

Secrets, enrollment credentials and secret URLs must not be emitted in telemetry/logs.

### Result logging

Task results include success/failure, detailed error on failure, duration and Worker version. Runtime task/step state is also emitted in heartbeat so Commander can show fleet progress.

## Compatibility and versioning

- Commander remains v5 while this contract is stabilized.
- Android Worker 0.4.x is the first generic recipe-engine baseline.
- `ui-sequence` remains supported for compatibility; `workflow-recipe` is the preferred semantic task type.
- New Worker capabilities are additive wherever possible.

## Stable acceptance gate

A change may be called stable only after all applicable checks pass:

1. repository lint/tests/build,
2. Android debug/release compile and signing workflow,
3. Commander launcher contract checks,
4. no business-specific stage branching inside the generic Worker cell-link primitive,
5. bounded retries and fail-stop semantics remain intact,
6. resident restart/reconnect code remains present,
7. physical-device E2E is explicitly marked verified or unverified; it must never be inferred from CI alone.
