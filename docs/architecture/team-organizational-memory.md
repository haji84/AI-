# Team Organizational Memory

## Principle
Dynamic teams are temporary execution structures, not disposable knowledge. A team may dissolve after a goal completes, but its capabilities, composition, procedure lineage, outcomes and verification history remain reusable organizational knowledge.

## Lifecycle
1. The orchestrator assembles the smallest supported team for the current goal.
2. A successfully executable team can be captured as a `TeamBlueprint`.
3. Outcomes update success, verified-success, failure and quality evidence.
4. Similar future goals rank prior blueprints by goal similarity and measured performance.
5. Recall always re-checks currently available capabilities. Missing capabilities make the old blueprint ineligible rather than being fabricated.
6. Changed conditions can produce a derived blueprint. The parent remains immutable historical evidence and the child starts with fresh performance statistics.
7. Repeated verified success can promote a blueprint to `standing_candidate`.
8. Repeated poor performance demotes a blueprint and prevents automatic recall.

## Meaning of standing team
`standing_candidate` does not mean an always-running agent or permanent compute allocation. It means a proven organization pattern is preferred for matching work and can be reassembled quickly. Runtime workers still exist only while needed unless a separate operational policy explicitly requires persistence.

## Learning boundary
Team memory stores evidence about **how to organize capabilities**. Procedural Memory stores reusable **how-to procedures/skills**. Episodic Memory stores individual execution histories. The planner may combine all three, but none may silently promote unverified outcomes into trusted knowledge.

## Safety
Organizational memory never bypasses capability availability, risk classification, Human Gates, verifier requirements, or retry limits. A previously successful team does not inherit permission for a new task. Every new goal is evaluated under current policy.
